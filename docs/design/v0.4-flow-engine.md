# v0.4 flow engine 設計文書

tilepage v0.4 で導入する flow engine の仕様。横書き (`horizontal-tb`) と縦書き (`vertical-rl`) で **同一エンジン** が走り、軸抽象 (axis projection) と JS 実測による chunking で「N 段に流す本のページ」を実現する。

評価軸 6 項目 (`plans/2026-05-14_v0.4-evaluation-criteria.md`) を全て満たす設計を以下に明文化する。

## 評価軸との対応

本設計は以下の評価軸 6 項目を満たす:

- **評価軸 #1**: text は 1 本の連続ストリーム、page は可変、resize で再分配 — `## flow 擬似コード` の book 単位ストリーム保持と `## resize 戦略` の page 動的追加/削除で担保
- **評価軸 #2**: 横書きも縦書きも同じ flow engine、duplicate 設計は両方捨てる — `## 軸投影関数仕様` で writing-mode 分岐を projection に閉じ込め、本文中で `duplicate` 戦略を **採用しない** ことを明記
- **評価軸 #3**: 段数は N (configurable)、6 はデフォルト値に過ぎない — `## 公開 API` で `createBook({ columns: N })` を仕様化、本文中の図解・擬似コードは全て N で表記
- **評価軸 #4**: px 固定なし、論理プロパティ + 1fr / % で軸抽象化 — `## 公開 API` と `## resize 戦略` でサイズ単位を `1fr` / `%` / `em` / `inline-size` / `block-size` に限定、`px 固定` の使用を否定文脈で明記
- **評価軸 #5**: 検証は visible text 文字数照合 (DOM 存在ベースは不可) — `## 検証関数 visibleTextOf` で Range + boundingRect ベースの仕様化、`elementFromPoint` を否定文脈で明記
- **評価軸 #6**: CSS でできないところは JS で測って切る — `## chunking アルゴリズム` で Range API + getClientRects + binary search による実測切断を仕様化

## 段の図解 (horizontal-tb)

横書き本の 1 ページ。inline 軸 = 横、block 軸 = 縦。**段** は inline 軸方向に幅を持ち block 軸方向に連結する **縦 strip**。N 段 (例として N=4 を描くが、N は configurable)。

```
┌─────────────────────────────────────────────────────┐
│ page (writing-mode: horizontal-tb)                  │
│ flow-layer: grid-template-columns: repeat(N, 1fr)   │
│                                                     │
│   col1       col2       col3       col4             │
│ ┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐           │
│ │A B C │   │M N O │   │Y Z a │   │k l m │  ← inline │
│ │D E F │   │P Q R │   │b c d │   │n o p │           │
│ │G H I │   │S T U │   │e f g │   │q r s │           │
│ │J K L │   │V W X │   │h i j │   │t u v │           │
│ │      │   │      │   │      │   │      │           │
│ └──────┘   └──────┘   └──────┘   └──────┘           │
│   ↓ block 軸方向に下に伸び、終端で次の段の頭へ       │
│                                                     │
│ obstacle (rect): col=2-3, row=1-2 の cell を占有     │
│   text は obstacle の下 (block 軸 = 下) に逃げる    │
│                                                     │
│ reading order: col1 → col2 → col3 → col4 →          │
│                次ページ col1 → ...                   │
└─────────────────────────────────────────────────────┘
```

ポイント:

- 段の幅は `1fr` (N 等分)、`px` 固定では書かない (評価軸 #4)
- 1 段の block 軸方向の終端に達したら、ストリームの続きは次の段の inline 軸の頭から流れる
- obstacle は block 軸方向に占有領域を持ち、text は obstacle の下に逃げる
- ページ末尾の段の終端でストリームが残っていれば、内部で `addPage` を発生させ次ページの col1 に続ける (評価軸 #1)

## 段の図解 (vertical-rl)

縦書き本の 1 ページ。inline 軸 = 縦、block 軸 = 横 (右 → 左)。**段** は inline 軸方向に高さを持ち block 軸方向に連結する **横 band**。N 段 (configurable)。

```
┌─────────────────────────────────────────────────────┐
│ page                                                │
│ flow-layer: grid-template-columns: repeat(N, 1fr)   │
│ flow-layer 全体に writing-mode: vertical-rl         │
│   → CSS Grid の軸が swap され band が並ぶ            │
│                                                     │
│   band1 (一番上)                                    │
│   ┌─────────────────────────────────────────────┐   │
│   │ J G D A    ← inline 軸 (縦) は文字が下方向 │   │
│   │ K H E B       block 軸 (横) は右→左         │   │
│   │ L I F C                                     │   │
│   └─────────────────────────────────────────────┘   │
│   band2                                             │
│   ┌─────────────────────────────────────────────┐   │
│   │ V S P M    ← band1 の左下から続いて          │   │
│   │ W T Q N       band2 の右上に折り返す         │   │
│   │ X U R O                                     │   │
│   └─────────────────────────────────────────────┘   │
│   ...                                               │
│   bandN (一番下)                                    │
│                                                     │
│ obstacle (rect): row=1-2, col=1-2                   │
│   text は obstacle の左 (block 軸 = 左) に逃げる    │
│                                                     │
│ reading order: band1 → band2 → ... → bandN →        │
│                次ページ band1 → ...                  │
└─────────────────────────────────────────────────────┘
```

ポイント:

- 段の高さは `1fr` (N 等分)、`px` 固定では書かない
- 1 段の block 軸方向 (右→左) の終端に達したら、ストリームの続きは次の段の inline 軸 (縦) の頭から流れる
- obstacle は block 軸 (横) 方向に占有領域を持ち、text は obstacle の左に逃げる
- writing-mode は **flow-layer / obstacle-layer (column の親) 全体に適用**。`.tilepage-column` 単体には当てない (PR #3 の失敗パターン)

## flow 擬似コード

横書き / 縦書き共通の擬似コード。`writingMode` への分岐は **axis.ts の projection 内のみ** に閉じ込め、measure / chunk / distribute は分岐を持たない (評価軸 #2)。

```ts
// flow engine の中心ルーチン (擬似コード)
function flow(book: Book): void {
  const text = book._sourceText;           // book に保持された唯一のストリーム
  const projection = axisProjection(book.writingMode);

  // 1. measurement: 全 text を off-screen DOM に流して各文字の rect を取得
  const measured = measureAll(text, {
    inlineSize: book.windowInlineSize,     // 段 1 本の inline 軸サイズ
    fontStyles: book.computedTextStyles,
    projection,                            // rect → (inline, block) への投影
  });

  // 2. chunking: 各 page の各段に「何文字までが収まるか」を binary search
  let offset = 0;
  const pages: PageChunkPlan[] = [];
  while (offset < text.length) {
    const page = book.ensurePage(pages.length);
    const windows = page.windows(projection); // N 個の column / band
    const chunks: TextRange[] = [];
    for (const w of windows) {
      const end = chunkFor(measured, {
        from: offset,
        inlineSize: projection.inlineSizeOf(w),
        blockSize: projection.blockSizeOf(w),
        obstacles: w.obstacleSegments,     // window 内で占有された block 軸範囲
      });
      chunks.push({ from: offset, to: end });
      offset = end;
      if (offset >= text.length) break;
    }
    pages.push({ page, chunks });
    if (offset >= text.length) break;
  }

  // 3. distribute: 計算結果を実 DOM に反映 (duplicate しない、同じ chunk を複数 window に書かない)
  for (const plan of pages) {
    distribute(plan);                      // chunk を 1 個ずつ 1 window へ
  }

  // 4. 余剰 page の刈り取り: 旧 layout より page 数が減ったら削除
  book.trimPagesAfter(pages.length);
}
```

ステップごとの責務:

| step | 入力 | 出力 | 副作用 |
|------|------|------|--------|
| measurement | source text 全体、字形スタイル、window inline-size | `MeasuredText` (各文字インデックス → rect の projected (inline, block)) | off-screen DOM に一度だけ流す |
| chunking | `MeasuredText`, window 1 つの (inlineSize, blockSize, obstacles) | text の range `[from, to)` | なし (pure) |
| distribute | range と実 DOM の window 要素 | 実 DOM の `textContent` 更新 | flow-layer の DOM を書き換え |

**duplicate しないこと**:

- 旧 v0.3 `addFlow` は各 column へ同じ全文を duplicate 書き込みしていた → 本仕様では 1 つの chunk は **1 つの window にだけ** 書く
- source text は `book._sourceText` に 1 箇所だけ保持し、distribute は range slice を書き込む

**`px 固定` を使わないこと**:

- window の inline-size / block-size は `getBoundingClientRect()` の **実測値** をその場で渡す。CSS は `1fr` / `%` / `em` / `inline-size` / `block-size` のみ
- chunk 境界の決定にも `px` リテラルは現れない (実測 rect の数値だけ使う)

## 軸投影関数仕様

writing-mode に応じて inline 軸 / block 軸が物理座標 (x, y) のどちらに割り当てられるかが swap される。flow engine 本体は **物理座標を直接見ない**。すべて projection 経由でアクセスする。これにより評価軸 #2 (同一 engine) を実現する。

### 型定義

```ts
type WritingMode = 'horizontal-tb' | 'vertical-rl';

interface AxisProjection {
  readonly writingMode: WritingMode;

  // rect → 単一スカラ (論理軸座標)
  inlineAxisOf(rect: DOMRect): { start: number; end: number; size: number };
  blockAxisOf(rect: DOMRect): { start: number; end: number; size: number };

  // 要素全体の論理寸法
  inlineSizeOf(el: Element): number;
  blockSizeOf(el: Element): number;

  // reading order: window 配列を読み順に並べ替える
  readingOrder<T>(windows: ReadonlyArray<T>): ReadonlyArray<T>;

  // float を window の block-start 物理辺に寄せるための CSS 物理側。
  floatSide(): 'left' | 'right';
}

function axisProjection(mode: WritingMode): AxisProjection;
```

### 入出力の意味

| メソッド | horizontal-tb | vertical-rl |
|----------|---------------|-------------|
| `inlineAxisOf(rect)` | `{ start: rect.left, end: rect.right, size: rect.width }` | `{ start: rect.top, end: rect.bottom, size: rect.height }` |
| `blockAxisOf(rect)` | `{ start: rect.top, end: rect.bottom, size: rect.height }` | `{ start: rect.right, end: rect.left, size: rect.width }` (右→左で start > end になる) |
| `inlineSizeOf(el)` | `el.clientWidth` | `el.clientHeight` |
| `blockSizeOf(el)` | `el.clientHeight` | `el.clientWidth` |
| `readingOrder(ws)` | そのまま (左→右) | そのまま (上→下、band 順) |

`vertical-rl` の block 軸は右→左に進むため、`start > end` になりうる。chunk のアルゴリズムは projection の `start` / `end` のみを見て、物理符号を意識しない。

### writing-mode 分岐の閉じ込め

- `src/flow/axis.ts` (Sprint 3 で作成) **以外** のファイルには `vertical-rl` / `writingMode` の文字列リテラル分岐を書かない
- `chunk.ts` / `measure.ts` / `distribute.ts` は projection を引数で受け取り、`projection.inlineAxisOf(rect)` のような呼び出しだけを使う
- これにより評価軸 #2 (横書きも縦書きも同じ flow engine) を実装レベルで担保する

## chunking アルゴリズム

ある window (column / band) に「source text のどこからどこまでが収まるか」を **実測** で求める。CSS では決定できないので JS で測る (評価軸 #6)。

### 入力

- `measured: MeasuredText` — 文字 index → projected `(inline, block)` rect
- `from: number` — 流し始める text index
- `inlineSize: number` — window の inline 軸サイズ (projection.inlineSizeOf(window))
- `blockSize: number` — window の block 軸サイズ
- `obstacles: ObstacleSegment[]` — window 内で block 軸方向に占有された区間 (float / shape-outside の効果が反映された結果)

### 出力

- `to: number` — `[from, to)` がこの window に収まる範囲

### 手順

```text
1. lo = from, hi = text.length
2. while lo < hi:
     mid = (lo + hi + 1) / 2 (整数)
     if fits(measured, from, mid, inlineSize, blockSize, obstacles):
       lo = mid
     else:
       hi = mid - 1
3. return lo (= from + chunk 長)

fits(measured, a, b, IS, BS, obstacles):
  // measured[a..b] の各文字の rect を projection で見て、
  // - inline 軸が [0, IS] に収まり (はみ出した時点で改行が起きる前提)
  // - block 軸の最終位置が BS を超えず
  // - obstacles の区間と inline 軸方向で交差する文字行が回避されている
  //   (obstacle の block 軸区間中は inline 軸の利用可能幅が狭まる)
  // を判定する。
```

### 実 DOM への流し込み

`MeasuredText` は **off-screen の measurement DOM** に source text 全体を 1 回流して `Range` API + `Range#getClientRects()` で各文字の rect を取得することで構築する。

```ts
// measurement DOM の作成 (擬似コード)
const measurer = document.createElement('div');
measurer.style.position = 'absolute';
measurer.style.visibility = 'hidden';
measurer.style.inlineSize = `${windowInlineSize / 16}em`; // em / % / 1fr で書く
measurer.style.writingMode = book.writingMode;
measurer.textContent = book._sourceText;
hostDocument.body.appendChild(measurer);

const textNode = measurer.firstChild as Text;
const measured: MeasuredText = [];
for (let i = 0; i < textNode.data.length; i++) {
  const range = document.createRange();
  range.setStart(textNode, i);
  range.setEnd(textNode, i + 1);
  const rect = range.getBoundingClientRect();
  measured.push({
    inline: projection.inlineAxisOf(rect),
    block:  projection.blockAxisOf(rect),
  });
}
measurer.remove();
```

- `Range` API + `getClientRects()` で文字単位の rect を取る (評価軸 #6 の要求コア)
- 文字単位の measure を逐次やると O(N) で重いので、本実装では `getClientRects()` を range 単位でまとめて取得するなど最適化する (アルゴリズムの本筋は上記擬似コード)
- binary search で 1 window あたりの `fits` 判定回数を O(log N) に抑える

### obstacle の取り扱い

- `obstacles: ObstacleSegment[]` は projection 後の block 軸区間 `[blockStart, blockEnd]` と、その区間中に inline 軸方向で残された利用可能幅 `availableInlineSize` を持つ
- shape-outside / float による text の回避は既存の `src/utils/polygon.ts` が出した結果を ObstacleSegment に変換して chunking に渡す
- chunk アルゴリズム自体は **物理座標も writing-mode も知らない**。projection と segment だけを見る

## 公開 API

v0.4 で追加・変更される公開 API のシグネチャ。`src/index.ts` から re-export される。

```ts
type WritingMode = 'horizontal-tb' | 'vertical-rl';

// flow engine が JS 側で N を実数として扱う必要があるため、内部的には実測した N を

  container?: HTMLElement;

  text: string;
}

declare function addFlow(book: Book, options: AddFlowOptions): void;

// page は book に対して内部で動的に追加される。
// 明示的な addPage 呼び出しも維持 (v0.1 互換)、option を渡せる。
```

## obstacle 座標系

採用: **案 A (writing-mode-aware、CSS Grid 仕様準拠)**

### 仕様

- `addObstacle(page, { at: { col, row } })` の `col` / `row` は CSS Grid の `grid-column` / `grid-row` をそのまま意味する
- CSS Grid 自体が writing-mode で軸を swap する仕様なので、`writing-mode: vertical-rl` に切り替えた瞬間 `at` の解釈も swap される
- 例: `at: { col: 1, row: 1 }` は horizontal-tb なら左上、vertical-rl なら右上 (inline 軸の頭) を指す

### 根拠

| 観点 | 案 A (writing-mode-aware) | 案 B (物理座標固定) |
|------|---------------------------|--------------------|
| CSS Grid 仕様との整合 | ◯ そのまま | × ad-hoc な変換が必要 |
| v0.1 / v0.2 の既存 API との互換 | ◯ | × |
| ユーザーへの説明 | ◯「CSS Grid と同じです」 | △「内部で逆変換します」 |
| writing-mode 切替時の挙動の予測可能性 | ◯ inline / block 軸の概念で説明可能 | × 物理座標固定だと縦書きで意味が反転する |

→ 案 A を採用。物理座標固定が必要なユーザーは writing-mode を切り替えなければよい。v0.4 では writing-mode 切替時の物理座標固定 API は出さない。

### 内部実装

- `at.col` → `grid-column` プロパティに直接渡す
- `at.row` → `grid-row` プロパティに直接渡す
- 内部で writing-mode を読んで分岐する必要はない (CSS Grid が自動で軸 swap する)
- obstacle 占有領域を flow engine に伝える際は `getBoundingClientRect()` を取り projection で論理軸に変換する

## resize 戦略

ResizeObserver で book / page の `contentRect` 変化を監視し、stream 全体を再分配する。page 数は動的に増減する (評価軸 #1)。

### 状態遷移

```text
            ┌──────────────┐
            │   idle       │
            └─────┬────────┘
                  │ ResizeObserver fires
                  │ (book or page contentRect changed)
                  ▼
            ┌──────────────┐
            │   pending    │  (debounce window: 1 animation frame)
            └─────┬────────┘
                  │ frame elapsed
                  ▼
            ┌──────────────┐
            │  reflowing   │ ──┐  ← この間 isReflowing = true
            │  flow(book)  │   │     ResizeObserver 通知は無視 (無限ループ防止)
            └─────┬────────┘   │
                  │ done       │
                  ▼            │
            ┌──────────────┐   │
            │  draining    │ <─┘  ← reflow 中に積まれた notify をまとめて 1 回処理
            └─────┬────────┘
                  │
                  ▼
            ┌──────────────┐
            │   idle       │
            └──────────────┘
```

### page の動的追加・削除

```text
trigger: addFlow / addObstacle / resize による reflow
        │
        ▼
flow(book) を実行 → chunking で必要な page 数 P を算出
        │
        ├─ book.pages.length < P → 不足分 (P - book.pages.length) を ensurePage で生成
        │
        └─ book.pages.length > P → trimPagesAfter(P) で余剰 page を削除
```

### debounce / 無限ループ防止

- `isReflowing` フラグで reflow 中の ResizeObserver 通知を吸収
- 1 animation frame の debounce で連続発火 (mouse drag による resize 等) をまとめる
- reflow 完了後に積まれた通知が残っていれば 1 回だけ追加 reflow

### resize 中の visible text 保証

- reflow の各ステップ完了時点で `visibleTextOf(book) === book._sourceText` (V === S) が成立すること
- viewport を `1200 → 1800 → 1200` と動的に変化させる sweep test (Sprint 2 / Sprint 5) でこれを検証する

### width モードにおける N の動的導出

`columns: { width }` 指定時は N が viewport で変動する。reflow の各 cycle で以下を行う:

1. flow-layer の inline 軸 clientSize を実測 (padding 除外)
2. 指定 `width` を CSS 経由で px 解決
3. `floor((inline + gutter) / (width + gutter))` を最大 N とする (最低 1)
4. 既存 N と異なれば全 page の `.tilepage-column` 数を増減 (差分 DOM 操作)
5. CSS 変数 `--tilepage-columns` を新 N に更新

これにより:

- viewport を広げると N が増え 1 page あたり多くの段が並ぶ → page 数が減る
- viewport を狭めると N が減り 1 段あたり収容文字数が減る → page 数が増える
- flow engine 本体 (distribute / measure / chunk) は N の変化を意識しない。`windowsForPage(idx)` が常に最新の columnElements を返すため

## 検証関数 visibleTextOf の仕様

評価軸 #5: DOM 存在ベースの検証は不可。`visibleTextOf` は **「実際にユーザーが読める文字」だけ** を抽出する。`elementFromPoint` は overflow:hidden / clip の判定に弱いため **使わない**。

### シグネチャ

```ts
function visibleTextOf(book: HTMLElement): string;
// 戻り値: 読み順 (reading order) で連結した可視文字列
// 期待: source text と完全一致 (空白・改行含む)
```

### 抽出手順

```text
1. book 配下を TreeWalker で walk し、TextNode の集合 T を得る
2. T を flow-layer 上の reading order でソート:
     - horizontal-tb: column 順 → 各 column 内で上→下
     - vertical-rl:   band 順 → 各 band 内で右→左
   (実装では各 TextNode の親 window 要素の DOM 順 = reading order に整列している前提)
3. 各 TextNode tn について:
     for i in 0..tn.data.length:
       range = createRange(); range.setStart(tn, i); range.setEnd(tn, i+1)
       for rect in range.getClientRects():
         if isVisible(rect, tn): emit tn.data[i] (一度だけ)
4. 連結した文字列を返す
```

### `isVisible(rect, textNode)` の判定

`rect` が以下のすべてを満たす時のみ visible:

1. `rect.width > 0 && rect.height > 0`
2. book ルートの `getBoundingClientRect()` 内に rect が収まる (intersection が rect 自身と一致)
3. textNode の祖先要素 chain を辿り、すべての overflow を持つ祖先 (`computedStyle.overflowX|Y in {hidden, clip, scroll, auto}`) の `getBoundingClientRect()` と rect が交差していること、つまり clip されていない

### **同一 textNode 由来の rect の duplicate ガード (重要)**

`Range#getClientRects()` は折り返し / 行末などで複数 rect を返す。同じ文字インデックス `i` について複数の visible rect が返っても **emit は 1 回のみ** とする。

```ts
// 擬似コード
const emittedChars = new Set<string>(); // key: `${textNodeId}:${i}`
for (const tn of textNodes) {
  const tnId = registerTextNode(tn); // WeakMap でユニーク ID
  for (let i = 0; i < tn.data.length; i++) {
    const range = createRange();
    range.setStart(tn, i); range.setEnd(tn, i + 1);
    const rects = range.getClientRects();
    let visible = false;
    for (const rect of rects) {
      if (isVisible(rect, tn)) { visible = true; break; }
    }
    const key = `${tnId}:${i}`;
    if (visible && !emittedChars.has(key)) {
      emittedChars.add(key);
      result += tn.data[i];
    }
  }
}
```

このガードがないと、distribute が誤って **同じ textNode を複数 column / band に共有** していた場合 (= duplicate 戦略の再来) でも `getClientRects` が個別 rect を返し、V が S の整数倍になって V === S が成立せず正しく FAIL するが、**逆に同一 textNode 由来の line-wrap で 1 文字が複数 rect になっただけのケースで V が S を超えてしまう false negative も起こりうる**。同一 textNode + 同一文字 index の rect は何回見ても 1 文字として数える、というガードで両方を排除する。

### 禁止事項

- `elementFromPoint` を使ってはならない (DOM 存在ベース判定への退行)
- `innerText` / `textContent` 単独での照合をしてはならない (`innerText` は CSS で `display: none` 等は除外するが overflow clip は除外しないため visible 判定として不十分)
- 文字数だけで V === S を判定してはならない (文字列としても完全一致を確認する)

## 否定事項のまとめ (PR #3 失敗パターンを設計上排除する)

本設計では以下を **採用しない**:

- **duplicate**: 各 column に同じ text 全文を流し込む戦略は採らない。source text は `book._sourceText` に 1 箇所だけ保持し、distribute は range slice を 1 つの window にだけ書き込む (評価軸 #2)
- **elementFromPoint**: 検証関数で `elementFromPoint` を使うのは禁止。overflow:hidden / clip で隠れた DOM も "存在する" と判定してしまうため、評価軸 #5 (visible text 照合) を満たせない
- **px 固定**: CSS にも公開 API にも `px` リテラルを書かない。`1fr` / `%` / `em` / `inline-size` / `block-size` / 論理プロパティのみを使う。例外は measurement DOM の off-screen 配置 (`-9999px` 等) のみで、コメント必須 (評価軸 #4)
- **`.tilepage-column` 単体への writing-mode 適用**: PR #3 で破綻したパターン。writing-mode は flow-layer / obstacle-layer (column の親) に適用する
- **DOM 存在ベースの E2E 検証**: overlap 0 件だけを成功指標にしない。V === S (visible 文字数 + 文字列完全一致) で評価する
